{% extends "guide-base.html" %} {% block heading %}A support form that emails you{% endblock %} {% block standfirst %}The form on your docs or support page — topic, order number, and the issue itself — with every request delivered to one inbox.{% endblock %} {% block about %}

When something goes wrong, customers look for a support page. A form there beats a bare email address: you ask for the order number and topic up front, so the first email already has the context you need instead of arriving as "it doesn't work".

If your docs or support page is a static site, it can't receive the form POST itself. Form2Email receives it and emails you the request — every issue lands in the same inbox, and the customer's address is set as reply-to so you answer them directly.

That's the whole integration. The form works with or without JavaScript, on any host that can serve an HTML page. Style the fields however you like — only the action, method="post", and the input name attributes matter to Form2Email.

{% endblock %} {% block mapping %}

Each submission becomes one email to your destination address:

  • Reply-To is the customer's email, so hitting reply answers them directly.
  • The subject field becomes the email's subject line ("New form submission: …"), so threads stay scannable. Leave it out and you get a generic subject.
  • name and message appear in the body.
  • topic and order are listed as additional fields, along with anything else you add.

With _redirect set, the customer's browser is sent to your thank-you page (a 303 redirect) after a successful submit. Without it they get a small JSON response — fine for JavaScript-driven forms, less friendly for plain HTML.

{% endblock %} {% block tips %}
  • A topic select makes inbox filtering easy — set up a mail rule on the topic value and Shipping or Refund requests file themselves.
  • Keep subject in the form. It becomes the email's subject line, which keeps threads scannable in your mailbox list.
  • Keep the order number optional. Requiring it blocks customers whose question has no order behind it.
  • Reply normally — the customer's address is already the Reply-To, so your answer goes straight to them.
  • Add {{ settings.mail_from }} to your contacts so the verification and submission emails don't land in spam.
{% endblock %} {% block limitations %}
  • This is email, not a ticketing system — no ticket numbers, no threading, no status tracking. You manage the conversation in your mailbox; if you need queues and SLAs, this isn't the tool.
  • A support form is always-on, so remember the endpoint expires {{ settings.default_ttl_days }} days after verification — extend it for free from your manage page (extending also revives an expired endpoint), or ask the operator for a permanent endpoint.
  • Submissions are accepted only from the exact domain you registered. If your support page answers on both yoursite.com and www.yoursite.com, register the one your form is served from (or create one endpoint per hostname).
  • No file attachments — a file input for screenshots is dropped. Ask for a link instead.
  • Spam protection is origin checks plus per-IP rate limits with backoff; there is no CAPTCHA or honeypot yet.
